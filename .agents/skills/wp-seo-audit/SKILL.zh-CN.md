# wp-seo-audit — Athletik SEO 审计与诊断 V2（中文阅读版）

> 本文件是 `SKILL.md` 的简体中文翻译，仅供阅读。Codex 实际执行时仍以英文 `SKILL.md` 为技能入口和权威版本。

## 技能说明

为 `myathletik-child` WordPress 主题提供以证据为基础的 SEO 审计与诊断。适用于页面或全站审计、索引与抓取问题、Search Console 分析、关键词/页面机会、SEO 回退问题、Core Web Vitals、内部链接、Schema、元数据，以及部署后的 SEO 验收。

审计与诊断是只读操作；如果用户明确要求实施修改，可以通过相关项目技能和变更控制流程继续执行。

## 核心原则

产出的决策必须能够追溯到线上页面、源代码、Search Console、分析数据或市场证据。不要把通用 SEO 评分当作审计结果。

审计与诊断均为只读操作。如果用户明确要求修复，应先完成诊断，再使用相关实施技能。当前网站的任何 URL 变更都必须先调用 `wp-redirect-guard`。

## 首先读取项目事实来源

只读取当前请求所需的文件，按以下资料开始：

- `AGENTS.md` 第 2–6 节：定位、实体、URL 决策、文案与术语。
- `seo-tags.md`：已核准的 Title、Meta、H1、社交分享图片与 alt 信息真值。
- `docs/sitemap.md`：当前信息架构与页面归属。
- `docs/progress.md`：当前部署状态。
- `docs/seo/seo-process.md`：证据层级、样本门槛与复核周期。
- 在解读查询词、CTR 或索引状态前，读取 `docs/seo/gsc-data-log.md`。
- 在提出新的实施事项前，读取 `docs/seo/seo-implementation-checklist-v1.md`。

不要仅仅因为旧审计或通用检查清单提到某个问题，就重新启用一个已经被取代的历史事项。

## 选择最小且有效的证据路径

1. 明确用户所指的是本地环境、预发布环境还是生产环境。
2. 对于广泛审计、回退检查、索引诊断、性能测试或 Search Console 机会分析，读取 [`references/seo-cli-routing.md`](references/seo-cli-routing.md)，并在手动探索前使用其中描述的一份结构化报告。
3. 对于范围较窄、仅涉及源代码的检查，直接检查相关源代码和生产环境渲染后的 HTML；不要运行无关报告。
4. 阅读返回结果中的每一项发现、覆盖范围字段、警告、限制说明和清单行。在评估完成前，绝不能截断结构化 JSON 结果。
5. 只有当证据需要实施上下文或真值来源对比时，才检查主题源代码。

## 结合项目实际的审计检查

### 可索引性与元数据

- 确认 HTTP 状态、robots meta、X-Robots-Tag、canonical、Sitemap 收录情况，以及可被发现的内部链接。
- 将渲染后的 Title、Meta 和 H1 与 `seo-tags.md`、`docs/sitemap.md` 对比；生产环境的真值是 Rank Math 的实际输出，而不是未启用的 PHP 数组。
- 将约 60 个字符的标题和约 155 个字符的描述视为宽松的复核参考。不能仅因长度，或在未达到 `seo-process.md` 数据门槛时，就改写内容。

### 标题层级与内容归属

- 每个页面必须恰好有一个 H1，并具有逻辑清晰的 H2/H3 层级。
- 确认一个主要搜索意图只归属于一个 URL。在诊断关键词蚕食前，先检查 GSC 中查询词与页面的重叠情况。
- 搜索结果页出现意图分裂，只能作为进一步调查的证据，不能自动视为创建两个页面的许可。

### 图片与媒体

- 每个 `<img>` 都必须有 `alt` 属性。信息型图片需要简洁、描述性的 alt 文本；装饰性图片应使用 `alt=""`。
- 如果使用文件名、关键词列表或无关词语作为 alt 文本，应标记为问题。
- 不要假设首页图库已经损坏；必须核验当前实际渲染结果。
- 根据实际情况检查固有尺寸或稳定宽高比、响应式候选图片、MIME/HTTP 状态、加载方式、解码方式及 LCP 优先级。

### URL 与内部链接规则

- 当前商业分类页使用顶级 `*-manufacturer/` 路由。
- 当前阶段没有独立的 `/products/` 页面。分类页通过首页产品区、导航、上下文链接和 Sitemap 被发现。
- 已退役的 `myathletik.com` 域名及其候选 `/products/<x>/` 映射被明确排除在重定向范围之外。不要把缺少这些重定向标记为问题。
- 今后若要更改 `athletikapparel.com` 上的线上 URL，必须在编辑前调用 `wp-redirect-guard`，并要求提供明确的 301 映射。
- 页面只要至少有一个可抓取且相关的内部入口，就不属于孤立页面。不要仅为增加链接数量而强制添加无关的同级页面链接。

### Schema 与实体信号

- 解析每一个 JSON-LD 区块，并将其类型和事实与页面可见内容进行对比。
- 仅仅存在 Schema 并不代表通过。应验证适用页面类型的必填字段，同时将可选增强项与错误分开处理。
- Athletik Clothing、Athletik Clothing Inc.、Zhangjiagang Athletik Clothing Co., Limited，以及不公开的 Beta Textiles 关系，都必须遵守 `AGENTS.md` 规定的边界。
- Schema、`llms.txt` 或允许 AI 爬虫访问，都不能代替有用且可索引的内容或独立引用来源。

### 性能与渲染

- 静态检查涵盖 LCP 加载优先级、首屏以下内容的懒加载、尺寸、响应式图片、字体显示、预连接和阻塞资源。
- 已接受的生产基线是仅加载一份子主题 `style.css`；没有证据时，不要恢复或接受重复的父主题样式表。
- 当性能是关键问题时，应同时使用 Lighthouse 实验室数据和可用的 CrUX 真实用户数据，并清楚地区分二者。源站级 CrUX 结果不能作为页面级证据。

## 问题发现契约

每一项 Critical（严重）或 Warning（警告）级发现都必须包括：

- 稳定 ID，以及 `fix`（修复）或 `review`（复核）类型；
- 受影响的 URL 和证据来源；
- 数据状态：完整、部分、抽样、达到上限、已跳过或不可用；
- 观察到的证据，并与推断分开记录；
- 可证伪条件；
- 最小化的建议操作；
- 验证方法和复核周期；
- 允许的结果：修复类使用 `fixed`、`deferred`、`not-needed`；复核类使用 `changed`、`no-change`、`deferred`。

交接时不得遗漏工具发现的任何问题或清单行。如果结果存在分页，必须取回每一页；否则应准确说明仍有哪些内容未经复核。

## 输出要求

返回以下内容：

1. 按严重程度排列的问题发现，并包含上述完整的问题发现契约；
2. 已通过的检查；
3. URL/重定向说明；
4. 根据预期业务收益、风险和工作量排序的后续行动；
5. 证据缺口，以及重新开启每个延期事项所需满足的确切条件。

## 证据纪律

- 将线上抓取、源代码、GSC、GA4、询盘数据、SERP 快照和第三方估算分别记录，不要混为一谈。
- 数据部分缺失或完全缺失不等于零，也不能据此得出“一切正常”的结论。
- GSC 分组汇总可能少计；查询词、页面、国家/地区和设备表之间不能相互替代。
- 第三方提供的搜索量、难度、权威度、流量和 AI 可见度属于估算，并非 Google 的测量数据。
- 不要承诺索引、排名、流量、询盘或 AI 引用结果。
- 不要把固定字数、关键词密度、通用 E-E-A-T 评分或单一的 0–100 审计分数作为触发修改的依据。
- 绝不能编造事实或长篇文案。遵守 `AGENTS.md` 的审批要求和证据边界。
- 遵守实施检查清单中的禁止事项：不得堆砌关键词、创建门页、自动生成近重复页面、批量建设低质量链接，或添加缺乏依据的 Schema。
